# 导航与大脑的反馈闭环

人物侧负责感知、减停、局部重规划和物理行走；大脑负责目标选择、任务继续和失败后的求助或替代方案。可视化、模型描述和“找到路线”都不能替代实际到达。

## 使用

1. 启动 `python brain_server.py` 和 `python body_3d.py`，打开 `http://127.0.0.1:8080`。
2. 展开“咨询台途中障碍测试”，选择正常通行、双障碍绕行或完全堵路，点击“加载场景（再连接大脑）”。
3. 人物就绪后连接大脑。手动模式下可输入“请到咨询台来”；自动模式由工作人员和顾客继续对话。场景只能在断开且没有运行中动作时切换。
4. “只测试人物行走”是独立的本地行走测试，不连接大脑。它不能证明大脑反馈链路已运行。
5. 完全堵路时，人物在有限恢复后报告失败，由大脑求助、等待、选择合理的其他目标或放弃。可点击“移除路障”施加环境扰动：移除操作不直接恢复人物行走，必须等身体重新观测并确认路线安全，再通知大脑。

无语音识别模型时，大脑可用 `python brain_server.py --no-asr`，手动输入文字。视觉辅助可保持关闭；几何避障和本闭环均不依赖VLM。实际模型调用仍需要现有GLM配置。

## 手动验收完全堵路

1. 断开已有连接，选择“完全堵路”，点击“加载场景（再连接大脑）”，再选择“手动：我扮演机器人”并连接大脑。
2. 如果顾客尚未开始前往咨询台，输入“请到咨询台来，我会在那里继续帮助您”。
3. 先保持路障不动。`braking/waiting` 表示人物仍在减停或尝试规划，尚不算最终失败；等待出现 `failed` 和失败反馈，再检查顾客是否求助或等待，而没有声称已经到达。受阻预算是120仿真秒，实际等待时间取决于倍速和电脑性能。
4. 道路未改变时，可以再说“请再试着走到咨询台来”。应保持目标暂不可达，不能仅凭这句话重复同一行走任务。
5. 点击“移除路障”。按钮只改变场景，接下来应先出现身体重新观测确认可达的记录，再由大脑决定是否重发 `walk_to`。如果顾客选择等待确认，可在可达证据出现后继续明确指引。
6. 等待人物实际到达并站稳，再检查是否收到完成反馈及新的对话。不要把“恢复可达”或“已下发命令”当成已经到达。

## 结果和过程

- `action_progress`：同一个命令的减停、规划中、恢复行走阶段。包含命令ID、目标、递增seq和导航摘要；服务端只记录监控，不因此调用模型或终止动作。
- `action_feedback`：最终结果，保持已有 completed / failed / interrupted。行走额外携带 target、reason、time、navigation。导航摘要包含成功重规划次数、规划尝试次数、受阻时长、来源、最后规划错误和暂不可达/可重试目标。
- `action_done`：语音结束且物理完成后触发下一轮决策。行走仍要求目标地点匹配、距离小于8厘米并站稳。
- `action_failed`：最终失败后触发大脑决策。身体停止、保持真实失败状态，不因说话或新截图改成成功。
- `navigation_available`：先前失败的目标经过新的深度观测和路线检查恢复可达。关联原失败命令，单次消费；该事件只允许大脑重新评估，不直接执行行走。

`state.navigation` 和 `Observation.navigation` 提供精简的导航上下文，不传整个地图或实物位置表。不可达状态跨工作人员说话、小动作等后续轮次保留；“请再试一次”本身不能解锁。`unavailable_targets` 阻止同目标盲目重复，其他合法目标仍可选择。`retryable_targets` 表示有身体提供的新可达证据，模型可结合任务决定是否重试。

局部恢复仍每2仿真秒尝试一次，受原有120秒受阻处理和12次成功重规划上限约束。失败后每2仿真秒重新观测受阻目标；预算耗尽的目标还要求地图发生变化。跌倒、物理超时等需要外部帮助，不能仅靠同目标重发解决。重新观测不会把上一条失败回执改写成成功。已失败目标的可达性在暂时空闲时更新，运动期间继续由当前命令持有控制权。

旧协议字段保持兼容；新增导航字段可选，旧2D身体仍可只发送最终动作结果。发送新进度消息的3D身体应与本版大脑服务一起更新。

## 检查与证据范围

- `npm.cmd run test:actions`：动作实际完成条件、进度去重、结构化失败。
- `npm.cmd run test:local-navigation`：有限恢复、清除旧占用、可达性更新；头部小幅移动后，旧点投影到新深度像素，只有新距离明确更远才清除，近处遮挡仍保留旧点。
- `python -m unittest discover -s tests -p "test_*.py"`：反馈校验、重复/乱序防护、跨轮失败目标约束、恢复事件一次性消费及员工上下文。
- `npm.cmd run test:navigation-loop`：真实浏览器桥接、WebSocket、大脑会话；并运行正常通行、双障碍和完全堵路的真实MuJoCo物理场景。模型供应商由固定响应替代，故意在失败后再次提出同目标行走，验证执行约束能拒绝它。堵路场景还检查移除后重新观测、大脑重新决策和实际到达。

`-- --bridge-only` 只检查桥接；`-- --cases=detour,blocked` 选择物理用例。完整物理验收需要数分钟，不会因仅生成一条路线就通过。正常/绕行要求到达反馈后有下一轮任务决策；堵路要求失败不假成功、后续说话不能盲目重试、有新可达证据后才能恢复。

## 2026-10-26 本地验收

真实物理、WebSocket、大脑会话三场景均通过：正常通行367.20仿真秒到达，最终误差约2.2毫米；双障碍绕行729.07仿真秒到达，重规划1次，最终误差约1.5厘米；完全堵路报告失败后，求助和后续无新证据的重试被正确处理，移除障碍并重新观测后重新派发，累计488.14仿真秒实际到达，最终误差约2.0毫米。全过程模型响应使用前述固定供应商fixture，以便可复现。

另外调用项目配置的GLM-5.3做了一轮真实失败决策检查：它收到堵路失败后选择挥手求助、保持任务进行中，没有重发不可达目标或宣称任务完成。这只是一轮模型检查，不代表所有对话分支都已在线验证。原有取号、叫号、到柜台和失败优先于终结状态的浏览器流程回归也已通过。

### 补充：真实模型完整堵路分支

同日使用生产浏览器页面、真实MuJoCo人物、真实WebSocket与GLM-5.3完成整段在线验收。本次关闭ASR/TTS，采用手动机器人文字交互，未替换模型响应或手动写入导航状态。

实际决策依次为：命令1前往咨询台 → 完全堵路后的最终失败 → 命令2挥手求助 → 道路未改变时工作人员要求再试 → 命令3原地等待 → 点击移除路障 → 身体重新观测并发送 `navigation_available` → 命令4重新前往咨询台 → 实际到达 → 命令5看向机器人并继续询问挂失补卡。

本次恢复行走由新的可达证据触发，无需移除后再催促。实际到达时刻约549.28仿真秒，位置误差约2.1毫米；原失败回执未被改写。共5轮真实模型决策，无被拒绝的动作反馈或页面脚本异常。完整消息与截图保存在本地 `logs/live-navigation-blocked.json`、`logs/live-navigation-blocked.png` 和 `logs/live-navigation-arrived.png`。这些属于本次验收产物，不进入Git。

本次证明这一具体堵路分支可闭环运行；不同任务、人设或其他障碍布局仍需单独验证，语音识别和合成不在本次在线验收范围内。

实现采用分层控制和有限恢复：快速执行由人物侧持有控制权，任务决策由大脑处理。本项目复用小型状态机和现有动作协议，没有引入ROS、行为树框架或新的动作模型。上述测试仅覆盖明确的本地场景，不代表真实机器人或任意障碍都已验证。

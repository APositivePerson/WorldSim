# 顾客 Agent 接口文档（v1）

可选视觉扩展：event 消息可附带 vision 对象，字段为 captured_at（仿真秒）、command_id（最近收到的命令 ID，首次为 null）、view（person）、phase（before_decision / after_action）、observation（结构化视觉结果）。服务器只采纳时间差 0–30 秒、命令匹配且类型合法的结果，放入下一轮 Observation.vision 后清空；缺失或非法视觉不影响原事件处理。详见 [视觉验证](视觉验证.md)。视觉结果不替代 action_feedback 或物理状态。

本文定义 Agent ↔ 页面之间已使用的 WebSocket 协议。人物技能层另按 [人物控制接口规范](小脑接口.md) 实现；该规范目前待代码接入，不改变本文的通信协议。人物侧的负责范围见 [人物侧开发职责](人物侧开发职责.md)。

给做人物模型（"身体"）的同学看。按这份文档实现，人物模型就能接上顾客大脑，大脑那边一行都不用改。
参考实现是项目里的 `env/body_2d.py`（2D 版身体），遇到不清楚的地方可以对照它。

## 1. 分工

```
┌───────────── 身体（你做） ─────────────┐        ┌──────── 大脑（Python） ────────┐
│ 场景、人物模型、动画、寻路             │ ──事件──▶│ ASR：把听到的声音转成文字       │
│ 播放顾客的语音                         │        │ GLM：决定说什么、做什么动作     │
│ 执行动作，动作完成/失败后回报          │ ◀─指令── │ TTS：把要说的话合成语音         │
└────────────────────────────────────────┘        └─────────────────────────────────┘
```

- **大脑**只知道"地点名"和"动作名"，不知道坐标。怎么走过去、动画怎么播，都由身体决定。
- **身体**要负责告诉大脑发生了什么：别人说了什么、动作做完没有、做不了的原因。

## 2. 连接

- 协议：WebSocket，消息都是 UTF-8 的 JSON 文本，每条消息用 `type` 字段区分。
- 大脑是**服务端**，身体是**客户端**。默认地址 `ws://localhost:8765`。
- 启动大脑：`python brain_server.py`。如果身体在另一台电脑上，用 `python brain_server.py --host 0.0.0.0`，身体连 `ws://<大脑电脑的IP>:8765`。
- 一个连接对应一位顾客。连接断开，这位顾客的这一场就结束了。
- 单条消息最大 16MB，带音频足够用。

## 3. 一场交互的完整流程

```
身体                                    大脑
 │── hello {persona:"wang"} ───────────▶│
 │◀────────────── ready {persona, actions, locations}
 │── event scene_start ────────────────▶│
 │◀─────────── status {thinking:true}   │（调 GLM 中，一般 2~5 秒）
 │◀─────────── command {speech:"", action:"walk_to", target:"help_desk"}
 │   （人物走向咨询台……）               │
 │── event action_done "你走到了咨询台" ▶│
 │◀─────────── command {speech:"你好啊，我卡丢了…", audio:"<mp3>", action:"wait"}
 │   （播放语音）                        │
 │── audio_done {id} ──────────────────▶│
 │── event robot_speech + audio ───────▶│（机器人说的话，带音频）
 │◀─────────── heard {text:"ASR 结果"}  │（调试用，可忽略）
 │◀─────────── command ...              │
 │                 ……                    │
 │◀─────────── command {action:"walk_to", target:"exit", goal_status:"done"}
 │── event action_done "你走到了出口" ──▶│
 │── bye ──────────────────────────────▶│
```

注意：
- 大脑每收到一条或几条事件，就会做一次决策、回一条 `command`。大脑正在思考时收到的事件会攒起来，下一轮一起处理，所以**身体不需要等 command 回来再发下一条事件**。
- 新的 `command` 可能在上一个动作还没做完时就到了，规则见第 6 节。

## 4. 身体 → 大脑

### 4.1 hello（连接后第一条，必须）

```json
{
  "type": "hello", "version": 1,
  "scenario": "bank",
  "persona": "wang",
  "body_profile": "human_3d",
  "capabilities": {
    "actions": ["wait", "walk_to", "wave", "nod", "shake_head", "look_at", "hand_over", "take"],
    "places": ["entrance", "help_desk", "ticket_machine", "waiting_area", "counter_1", "counter_2", "atm", "exit"],
    "look_targets": ["robot", "help_desk"]
  }
}
```

| 字段 | 必须 | 说明 |
|---|---|---|
| `scenario` | 否 | 场景 id，即 `scenarios/` 下的文件夹名（`bank`、`supermarket`……）。不传用大脑启动时的默认场景 |
| `persona` | 否 | 这个场景里的顾客人设，见 `scenarios/<场景>/personas.json`。不传用第一个 |
| `capabilities` | 否 | **身体实际能做的动作、能去的地点、能看的目标**。大脑取"场景提供的 ∩ 身体声明的"，只会让顾客用这些，提示词也据此生成。不传表示场景里的全部都能做 |
| `body_profile` | 否 | 身体类型名，对应场景文件 `profiles` 里的补充说明（比如 3D 身体走得慢、不能坐下）。不传则没有补充说明 |
| `mode` | 否 | `auto` 时由大脑这边驱动员工 Agent（见第 9 节），2D 身体不用传 |

**做不了的动作就不要声明**，比如 3D 身体还不能坐下，就不在 `actions` 里写 `sit`；场景里没有摆 3 号柜台，就不在 `places` 里写 `counter_3`。

### 4.2 event（发生了一件事）

```json
{
  "type": "event",
  "event": {"type": "action_done", "content": "你走到了1号柜台。", "time": 12.3},
  "state": {"time": 12.3, "location": "counter_1", "posture": "standing", "current_action": "wait"},
  "audio": "<可选，base64 编码的 mp3 或 wav>"
}
```

**event 字段**

| 字段 | 说明 |
|---|---|
| `type` | 事件类型，见下表 |
| `content` | 事件内容，**写给 LLM 看的中文**，用第二人称"你" |
| `time` | 场景时间，单位秒，从场景开始算 |

**事件类型**

| type | 什么时候发 | content 示例 |
|---|---|---|
| `scene_start` | 场景开始，顾客出现在起点 | 你走进了银行大厅，站在入口。 |
| `robot_speech` | 服务机器人（场景里的迎宾员工）说了一句话（**说完之后**再发） | 您好，请问办理什么业务？ |
| `teller_speech` | 其他工作人员（银行的柜员、超市的收银员……）说了一句话（说完之后再发） | 请出示您的身份证。 |
| `broadcast` | 大厅广播，比如叫号 | 请A023号顾客到2号柜台办理业务。 |
| `system_message` | 测试人员手动加的旁白 | 你发现身份证落在家里了。 |
| `action_done` | 顾客的动作完成了（见第 6 节） | 你走到了取号机。 |
| `action_failed` | 顾客的动作做不了 | 这里没有座椅，只有等候区能坐下。 |
| `navigation_available` | 原失败目标经身体重新观测和规划确认恢复可达，附原失败命令的 `command_id` | 咨询台恢复可达，请结合原任务决定下一步。 |
| `time_passed` | 很久没有任何动静（建议 25 秒） | 又过去了 25 秒，期间没有新的动静。 |

**state 字段**（每条 event 都带上，表示发这条消息时人物的状态）

| 字段 | 说明 |
|---|---|
| `time` | 场景时间（秒） |
| `location` | 当前所在地点的 key（见第 7 节）；正在走路时填 `"moving"` |
| `posture` | `standing` 或 `sitting` |
| `current_action` | 正在执行的动作名，空闲时填 `"wait"` |
| `navigation`（可选） | 身体提供的精简导航/恢复上下文，详见[导航闭环](导航闭环.md)。不包含完整地图。 |

**audio 字段（可选）**

- 只对 `robot_speech`、`teller_speech`、`broadcast` 有用：带上音频时，大脑会用 ASR 识别音频，**以识别结果为准**，`content` 里的原文只用来对比识别准不准。不带音频时直接使用 `content`。
- 格式：mp3 或 wav 文件的完整内容，做 base64 编码。采样率不限，大脑会自己转换。
- 以后接入真实的机器人，把它的声音录下来放进这个字段就行。

### 4.3 audio_done（顾客的语音播完了）

```json
{"type": "audio_done", "id": 3}
```

`id` 是对应 `command` 的 id。现在只用于记日志，以后做"说话被打断"时会用到。建议实现。

### 4.4 bye（结束）

```json
{"type": "bye"}
```

## 5. 大脑 → 身体

### 5.1 ready（回复 hello）

```json
{
  "type": "ready",
  "version": 1,
  "scenario": {"id": "bank", "name": "银行营业厅", "start": "entrance", "greeter": "robot",
               "staff": {"robot": {"label": "服务机器人", "places": ["help_desk"]},
                         "teller": {"label": "柜员", "places": ["counter_1", "counter_2", "counter_3"]}}},
  "persona": {"key": "wang", "name": "王阿姨", "age": 68, "gender": "女", "goal": "银行卡昨天在菜市场丢了……"},
  "actions": [{"name": "walk_to", "description": "走到某个地点", "targets": ["entrance", "..."]}, "..."],
  "locations": [{"key": "entrance", "description": "入口"}, "..."]
}
```

身体可以用 `persona` 选择人物模型（老人、年轻人……），用 `actions`、`locations` 检查自己是否都支持。
如果 hello 有问题，会回一条 `error` 并断开。

### 5.2 command（顾客要做的事）

```json
{
  "type": "command",
  "id": 3,
  "thought": "总算有人搭理我了，赶紧过去。",
  "speech": "哦哦，去1号柜台是吧，好，谢谢你啊。",
  "action": "walk_to",
  "target": "counter_1",
  "goal_status": "in_progress",
  "audio": "<base64 mp3，speech 为空时为 null>",
  "audio_seconds": 3.2,
  "latency": 3.1,
  "errors": []
}
```

| 字段 | 说明 |
|---|---|
| `id` | 指令编号，递增 |
| `thought` | 顾客的内心想法，**不要说出来**，可以显示在调试界面上 |
| `speech` | 要说出口的话；为空表示这一轮不说话 |
| `audio` | `speech` 的语音（mp3，base64）。身体负责播放 |
| `audio_seconds` | 语音时长，可以用来同步口型、气泡显示时长 |
| `action` / `target` | 要做的动作和目标，见第 6 节。大脑保证动作名和目标都合法 |
| `goal_status` | `in_progress` 进行中 / `done` 办完了 / `give_up` 放弃了。不是 `in_progress` 时，顾客通常会走向出口，走到后身体可以结束这一场 |
| `latency` | 这次决策用了多少秒，调试用 |
| `errors` | 大脑自动修正过的问题（比如 LLM 输出了不存在的动作），调试用 |

**说话和动作同时进行**：比如边走边说，或者边说边点头。

### 5.3 status / heard / error

```json
{"type": "status", "thinking": true}
{"type": "heard", "text": "你好，请问您要办理什么业务？", "original": "您好，请问您要办理什么业务？", "asr_time": 0.09}
{"type": "error", "message": "LLM 调用失败：..."}
```

- `status`：大脑开始/结束思考，可以用来在人物头上显示"思考中"，也可以让人物做一个想事情的小动作。
- `heard`：ASR 的识别结果，调试用。
- `error`：出错了，显示出来或者记日志就行，连接不会断。

## 6. 动作库

| action | 说明 | target | 完成后要回报吗 |
|---|---|---|---|
| `wait` | **保持当前动作不变**，只说话 | 无 | 不用 |
| `walk_to` | 走到某个地点。坐着时先站起来再走 | 地点 key | **要**，走到后发 `action_done`："你走到了XX。" |
| `sit` | 坐下，只能在有座椅的地点（场景文件 `workflow.seat_places`） | 无 | **要**，坐下后发 `action_done`；没有座椅发 `action_failed` |
| `stand_up` | 站起来 | 无 | **要** |
| `nod` | 点头 | 无 | 不用 |
| `shake_head` | 摇头 | 无 | 不用 |
| `wave` | 挥手（打招呼、叫人） | 无 | 不用 |
| `point_to` | 用手指向某处 | 地点 key 或物体 key（如 `robot`） | 不用 |
| `look_at` | 看向某处 | 地点 key 或物体 key（如 `robot`） | 不用 |
| `hand_over` | 递出东西（身份证、银行卡、商品） | 无 | 不用 |
| `take` | 伸手接东西 | 无 | 一般不用；**在取号机前做时要回报取到的号码**（见下） |

动作库本身和场景无关（`protocol.py` 的 `ACTIONS`），哪些动作这一场能用，由 hello 里的 `capabilities` 决定。

**执行规则**

1. `wait` 的意思是"不换动作"：人物正在走路的话就继续走，不要停下来。
2. 其它动作会**打断**还没做完的动作。比如走到一半收到 `look_at robot`，就停下来看机器人。
3. 点头、挥手这类小动作播完动画后回到待机（idle）就行，**不用回报**，免得大脑被打扰。
4. 做不了的动作发 `action_failed`，`content` 写清楚原因，大脑会换个做法。
5. `content` 用中文第二人称写，就像在告诉顾客"你感觉到了什么"。

**取号**（场景文件里有 `workflow` 时）：顾客在取号地点（银行是 `ticket_machine`）前做 `take`，身体要生成一个号码并回报：

```json
{"type": "event", "event": {"type": "action_done", "content": "你从取号机取到了号码 A023，号码纸上写着前面还有 3 人。", "time": 30.5}, "state": {...}}
```

之后到了时间，身体（或者叫号系统）发 `broadcast`："请A023号顾客到2号柜台办理业务。"

## 7. 地点和场景

地点、物体、员工都写在**场景文件**里（`scenarios/<场景>/scene.json`），不在代码里。银行场景的地点：

| key | 说明 |
|---|---|
| `entrance` | 入口（顾客出生点） |
| `ticket_machine` | 取号机 |
| `waiting_area` | 等候区，有座椅 |
| `counter_1` / `counter_2` / `counter_3` | 1/2/3 号柜台，柜员在柜台里面（3D 场景目前只有 1、2 号） |
| `atm` | ATM 自助取款机 |
| `help_desk` | 咨询台，服务机器人在这里 |
| `exit` | 出口 |

`look_at` / `point_to` 的目标除了地点，还可以是场景文件 `objects` 里的物体，比如 `robot`（服务机器人）。

**要增加或修改地点**：改场景文件。每个地点有 `label`（给 LLM 看的名字）、`pos2d`（2D 环境坐标，像素）、
`pose3d`（3D 站位 `[x, y, yaw]`，米/弧度，坐标约定见 `小脑接口.md`）。没写 `pose3d` 的地点在 3D 里去不了。
**要加新场景**：在 `scenarios/` 下新建文件夹，写 `scene.json` 和 `personas.json`，可以参考 `supermarket`。

## 8. 自测方法

1. 运行 `python brain_server.py`
2. 身体连上去，发 `hello` 和 `scene_start`，大约 3 秒后应该能收到第一条 `command`（一般是走向咨询台）
3. 走到之后发 `action_done`，再发一条不带音频的 `robot_speech`，比如"您好，请问办理什么业务？"，应该能收到带语音的回答

不想等 GLM、不想花钱时，可以用 `python brain_server.py --no-tts` 少做语音合成，加快速度。

## 9. 3D 扩展与后续计划

### 身体类型 body_profile（可选，协议版本仍为 1）

场景文件的 `profiles` 里可以给某种身体写补充说明，hello 里传对应的 `body_profile` 就会生效：

- `human_3d`：当前浏览器 3D 身体。补充说明"走路慢、要等 action_done、不能坐下"；能做的动作和地点由它自己在 `capabilities` 里声明。
- `human_demo`：原地对话联调。从咨询台开始，只用 `wait`、`wave`、`look_at robot/help_desk`，只做咨询不办业务。

`ready.actions` 只列出这一场实际能用的动作（场景提供的 ∩ 身体声明的）。

身体可发送小动作结果：

```json
{"type":"action_feedback","id":3,"action":"wave","status":"completed","message":"动作已达到目标并稳定"}
```

`id` 对应 `command.id`；`status` 为 `completed`、`failed` 或 `interrupted`。
服务器核对已发送命令的 ID、动作名和终态，回复 `{"type":"feedback_received","id":3,"accepted":true,"reason":null}`。未知 ID、动作不匹配、重复或冲突终态返回 accepted:false 和原因，不覆盖原结果。反馈可带 reason（如 timeout）。

反馈本身不触发 LLM，保留语音结束后再决策的顺序。最近 16 条动作记录通过 Observation.action_results 进入下一轮观察，含 id、action、target、status 及已有的 message/reason。pending 只表示尚未收到终态，wait 不覆盖正在执行的动作。

网页在语音结束后发送 action_done/action_failed 时，在消息顶层附带 command_id。服务端只接受最新动作已收到终态后的一次关联事件，过滤重复及过期事件。旧客户端不传 command_id 时仍兼容。取号等业务结果可能与伸手物理结果不同，由业务事件说明。

本轮含 action_failed 且模型原样重试最近失败的动作和目标时，Agent 将输出改为 wait、in_progress 并请求帮助。3D导航另外通过 `state.navigation.unavailable_targets` 跨对话轮次保留不可达目标，后续说话或小动作不能直接解锁；只有新的 `retryable_targets` 可达证据才允许重试，其他合法目标仍可选择。该保护依赖身体上报，不推测旧客户端未上报的结果。多技能拆解仍由人物适配层负责。
此消息不触发 LLM 决策，不代替原有导航等动作的 `event action_done/action_failed`。
3D 小动作使用它避免反馈引发自动对话循环。`wait` 不回报、不打断当前动作。
银行页面优先使用 `performAction` 和带命令 ID 的 `actionResult`，按物理完成结果反馈；`wave` / `nod` / `shake_head` 为分段动作，`take` / `hand_over` 为手掌 IK 伸手，左/右转头仍对应 `turn_head_left/right`。
动作接受后须等控制器完成，不能在接口返回 `true` 时立即报成功。伸手还要求实际手掌误差小于 2.5 厘米。没有 `performAction` 的旧身体仍兼容原有固定关节动作检查。

### 导航反馈扩展

`walk_to` 可在原 `action_feedback` 中附加 `target`、`time`、`reason` 和 `navigation`。摘要包含 `status/target/location/distance`、`replans`（成功次数）、`planningAttempts`（尝试次数）、`blockedTime`、`failureCode`、`lastPlanningError`、`unavailable_targets`、`retryable_targets`。`reason` 例如 `arrived`、`blocked_timeout`、`replan_limit`、`fallen`、`navigation_timeout`。服务端检查到达声明中的目标和距离，导航的完成/失败事件也须与终态一致；伸手后取号等业务判定仍可独立失败。

非终态过程使用单独消息，不覆盖最终结果，也不唤醒模型：

```json
{"type":"action_progress","id":3,"action":"walk_to","target":"help_desk","seq":1,"time":100,"phase":"blocked","navigation":{"status":"running","target":"help_desk","replans":0,"planningAttempts":0}}
```

`phase` 为 `blocked/replanning/moving`，只在阶段或成功重规划次数变化时发送。服务端只接受当前未完成的行走命令和递增seq。最终失败后，身体仍可继续观测；重新确认安全路线时通过 `state.navigation.retryable_targets` 和关联原失败命令的 `event navigation_available` 通知大脑。该事件按原命令去重，不把旧失败改成成功。界面和验证方法见[导航闭环](导航闭环.md)。

### 自动咨询扩展

`hello` 同时传 `body_profile` 和 `"mode":"auto"`，大脑为此会话创建员工 Agent（场景里的全部工作人员）。
客户端收到 `ready` 后发送 `{"type":"staff_request","command_id":null}` 发起机器人问候，
不再发送 `scene_start`。后续请求的 `command_id` 必须是已完成播放和动作的最新顾客指令编号。
服务端拒绝重复轮次及过时编号，每个连接最多 20 个员工轮次。

服务器返回 `staff_status {thinking}`，然后返回：

```json
{"type":"staff_command","id":"staff-1","turn":1,"speaker":"robot","label":"服务机器人","speech":"您好，请问办理什么业务？","audio":"<base64 mp3 或 null>","errors":[]}
```

`speaker` 是场景里的员工 key（`ready.scenario.staff`），`label` 是显示用的名字（柜员会带上柜台，如"柜员（1号柜台）"）。
员工只会在自己的岗位附近说话，大脑已经保证了这一点。
员工语音播完后，客户端回报 `audio_done`（此时 id 是 `staff-1` 字符串），
并把员工的话作为 event 发给顾客：迎宾（`ready.scenario.greeter`）发 `robot_speech`，其他员工发 `teller_speech`。
**事件里带上 `audio`（就是 staff_command 里的那段语音）**，大脑会用 ASR 听写，和 2D 一样。顾客语音和动作都结束后，
才发送下一条 `staff_request`。无音频时保留短暂文字阅读时间。
`speaker:none`、顾客 `goal_status` 结束、`auto_finished {message}` 均停止自动流程。
暂停由客户端保存队列、暂停播放和物理；已经在途的模型调用可能继续完成，但暂停期间不发起下一轮。
结束时发送 `bye` 并断开，旧连接的回答不进入新会话。
员工咨询内容、小动作回报和双方 `audio_done` 均记录到当前会话日志。

### 3D 物理行走：human_3d

当前浏览器发送 `hello {body_profile:"human_3d", mode:"auto", scenario:"bank", capabilities:{...}}`，
`capabilities` 来自页面的 `window.human.capabilities()`：地点是场景文件里写了 `pose3d` 的那些（没有 3 号柜台），不能坐下/起立。

`event` 和 `staff_request` 附带实际 `state` 及可选的 `bank`：

```json
{"type":"staff_request","command_id":6,"state":{"time":750,"location":"counter_1","posture":"standing","current_action":"wait"},"bank":{"ticket":"A001","called_counter":"counter_1","waiting_seconds":0}}
```

`walk_to` 接受后只表示导航启动，不能回报已到达。前端等待脚底支撑、根部速度、实际位置和朝向稳定后回报 `action_feedback`，待本句语音结束再发送 `event action_done`。
失败则发送 `event action_failed`；即使原指令是 `goal_status:done`，失败也不能直接结束会话。
导航期间 `state.location` 为 `moving`。本阶段使用固定地图 A* 和可视路径简化，底层以关节执行器控制脚步，不直接修改运行中的根部状态。

`take` 在取号机前完成伸手且站稳时生成号码；重复操作保留号码。取号完成事件包含号码和等候指引。
等候区站稳累计16秒仿真时间后只生成一次 `broadcast`；暂停不推进计时，广播会等待当前动作和语音处理完成后送给顾客。
这是单顾客逻辑排队演示，取号/递交物品为抽象交互，不包含手指按钮接触和纸张抓取。

员工说话时，客户端按上面的规则发送 `robot_speech/teller_speech`。
行走、取号事件先交给顾客决定下一步，不同时请求员工。顾客在等候区等叫号时，不因空 `wait` 或员工沉默而结束。
其他情况下员工无后续回应、20轮上限或成功执行终止指令后结束。断开连接会请求物理减停；重新连接保留场景，用户显式重置才恢复入口和空号码。

### 头部深度、高程地图与途中视觉检查

视觉输出新增 `path_obstacle: "suspected" | "clear" | "uncertain"`，缺省 `uncertain`。浏览器以 `during_navigation` 阶段观察当前人物视野，该阶段供本地导航检查使用，不作为服务器决策事件的 `vision.phase` 发送。

`window.human.reportVisualObstacle()` 仅在导航运行、当前路线已被高程地图判为受阻时返回 true 并请求停步。`navigation.obstaclePhase` 为 `none/braking/waiting`，`obstacleSource` 为 `vision/depth_elevation` 或空串；`replans` 表示本命令成功重规划次数，`observedCells` 是高程格数量，`observedVoxels` 是三维占用体素数量。头部深度独立运行，不依赖视觉模型开关。

停步后根据局部地图重新规划绕行，保持原任务目标；没有路线时等待观察，处理超过 120 仿真秒回报失败。单任务最多 12 次成功重规划。规划成功不等于动作完成，最终仍检查物理到达。

导航构造函数只接收人物控制器和可替换的深度帧函数，不接收测试路障列表。深度帧为 `origin{x,y,z}`、`yaw`、`range` 和 `rays[{dx,dy,dz,distance,hit}]`，不含物体 ID 或完整包围盒。测试入口 `/bank/?obstacle=1&height=low` 随机横向放置 20 厘米路障；`removeTestObstacle()` 仅改变环境碰撞和显示，不调用导航恢复。具体感知限制见[局部感知导航](局部感知导航.md)。
